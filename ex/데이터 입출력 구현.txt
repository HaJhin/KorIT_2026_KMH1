관계(Relation)
- 엔티티와 엔티티가 어떤 연결을 가지는지 표현하는 것
- 관계는 보통 동사 형태를 사용한다.
- 1:1 관계
- 1:n 관계
- n:m 관계 -> 관계형 DB에서 n:m관계는 중간 테이블을 하나 더 만들어서 1:n 관계로 해소시켜야 한다.

데이터 모델링 목적
- 연관 조직의 정보요구에 대한 이해를 할 수 있다.
ex) 회사나 사용자가 어떤 정보를 필요로 하는지 파악할 수 있다.
ex) 같은 내용을 그림이나 모델로 표현하면 서로 다르게 해석하는 문제가 줄어든다.
- 데이터 체계 구축을 통한 고품질 S/W와 유지보수 비용의 감소효과
ex)처음부터 데이터를 체계적으로 설계하면 나중에 수정할 일이 줄어든다.
- 신규 또는 개선 시스템의 개발 기초를 제공한다.
ex) 시스템 개발 시 데이터 모델은 설계도 역할을 한다.

데이터 모델링을 하면 무결성을 보장할 수 있다.
무결성
- 데이터가 정확하고, 일관성 있고, 신뢰할 수 있는 상태로 유지되는 것

1. 개체 무결성
- 각 행을 구분할 수 있어야 한다.
- 기본키는 중복이 되서도 안되고, NULL값도 가질 수 없다.
2. 참조 무결성
- 다른 테이블을 참조할 때, 존재하는 데이터만 참조해야 한다.

3. 도메인 무결성
- 컬럼에 허용된 값만 저장해야하는 원칙

4. 사용자 정의 무결성(CHECK)
- 업무 규칙에 맞는 데이터만 저장해야 한다는 원칙

개념
- 주요 엔티티타입, 기본 속성, 관계, 주요 업무를 포함한다.

- 모든 업무 데이터를 규격화 하여 모델링한다.
- 규칙과 관계를 완전하고 정확히 표현한다.
물리

정규화(Normalization)
- 중복성을 최소화하고 정보의 일관성을 보장하기 위한 개념
- 데이터 중복 배제로 데이터 관리 편의성 제고 및 자료 저장 공간의 최소화

정규화를 하지 않았을때의 문제점
1. 삽입이상
- 새로운 데이터를 넣으려고 할 때 원하지 않는 데이터도 함께 넣어야하는 문제
2. 갱신이상(수정 이상)
- 하나의 정보를 수정할 때 여러 곳을 모두 수정해야 하는 문제
3. 삭제이상
- 데이터를 삭제했는데 원하지 않는 정보도 함께 삭제되는 문제
필요 없는 데이터를 삭제하다가 필요한 정보도 같이 삭제되는 문제

함수적 종속성
- 어떤 컬럼이 다른 컬럼의 값을 결정하는 관계
A -> B
A가 B를 결정한다
B는 A에 함수적으로 종속된다.
A값을 알면 B값을 정확히 알 수 있다.

함수적 종속성의 종류

1. 완전함수종속(Full Functional Dependency)
- 기본키 전체에 의존하는 경우

2. 부분 함수 종속(Partial Dependency)
- 기본키 일부만으로 결정되는 경우

부분함수 종속의 문제점
- 데이터 중복과 이상현상을 발생시킨다.

3. 이행 함수 종속(Transitive Dependency)
- A가 B를 결정하고, B가 C를 결정하는 경우

4. 다치 종속(Multivalued Dependency)
- 다치 = 여러 개의 값
- 하나의 값에 여러 개의 값이 연결되는 것

5. 조인 종속(Join)
- 테이블을 여러 개로 나누었을 때, 다시 조인하면 원래 테이블로 정확히 복원되는 관계

제 1 정규화 (1NF)
- 모든 속성은 반드시 하나의 값을 가져야 한다.

제 2 정규화 (2NF)
- 부분 함수 종속을 제거한다.

제 3 정규화 (3NF)

제 4 정규화
- 다치종속 제거하기
- 관계가 없는 속성을 분리하기

제 5 정규화
- 테이블을 분해했을 때, 다시 조인하면서 가짜 데이터가 생기지 않도록 만드는 것

정규화를 진행하게 되면
- 유연한 데이터 구축이 가능
- 데이터의 정확성이 높아진다.
단점
- 물리적 접근이 복잡
- 길이가 짧은 데이터 생성으로 과도한 조인 발생

모델 작성 기법
- ERD를 그릴 때 엔티티와 관계를 보고 이해하기 쉽게 배치하는 방법
- 업무 흐름이 잘 보이도록 정리해서 배치하는 규칙

엔티티들은 정렬하여 배치한다.
- 무작위로 배치하지 않고 줄을 맞춰 정렬해서 배치

업무흐름의 진행 순서와 관련된 엔티티들은 진행순서를 고려하여 좌에서 우, 위에서 아래로 배치한다.

중심에 배치된 엔티티와 관계를 가진 엔티티를 가까이 배열한다.

관계는 사선이 아닌 수직, 수평선을 사용한다.

엔티티를 너무 붙히지 않고, 적절한 간격을 둔다.

논리 모델링 검증
- 데이터베이스를 실제로 만들기 전에 분석한 데이터 구조가 업무에 맞게 잘 정리되었는지 확인하는 과정

1. 시스템을 만들기 위해 필요한 데이터를 파악했는지
- 입력데이터, 출력데이터가 파악됐는지
- 데이터가 다른 업무나 시스템에서도 사용하는지 파악
- 새롭게 필요한 데이터가 있는지 파악

2. 현재 운영중인 시스템의 데이터현황 분석이 이루어졌는지 확인
- 데이터베이스 구조, 분산, 백업 현황이 정확히 파악되었는지
- 데이터 속성, 공통코드가 정확히 파악되었는지
- 외부 연계 데이터 속성이 정확히 파악되었는지

3. 데이터베이스에 대한 사용자 요구사항이 도출되고 분석되었는지
- 볼륨, 분산구조, 제약조건에 대한 요구사항이 도출되고 분석되었는지 확인
- 타 시스템과 연계 데이터에 대한 요구사항이 도출되고 분석되었는지 확인
- 데이터베이스 백업 및 복구 정책에 대한 요구사항이 도출되고 분석되었는지 확인
- 초기 데이터 구축 방안에 대한 요구사항이 도축되고 분석되었는지 확인
- 기존 데이터의 전환 방안에 대한 요구사항이 도출되고 분석되었는지 확인
- 무결성, 데이터 보안성 수준에 대한 요구사항이 도축되고 분석되었는지 확인

4. 데이터의 흐름이 명확하게 정의되었는지 확인
데이터의 흐름 : 데이터가 어디서 생성되고, 어디로 이동하며, 어디에서 사용되는지 나타내는 것

- 프로세스별 입출력 데이터가 명확히 정의되었는지 확인
- 프로세스 간 공유 및 연계 데이터가 명확히 정의되었는지 확인한다.
ㄴ 하나의 데이터는 여러 프로세스에서 공유될 수 있다.

5. 데이터베이스 설계 기준이 적절히 정의되었는지 확인한다.
- 데이터베이스 설계 표준 지침의 작성 여부 및 적절성 확인
ㄴ 데이터베이스 설계 표준 지침 : 테이블,컬럼,제약조건을 어떻게 작성할지 정한 문서
- 데이터 모델 설계 지침의 작성 여부 및 적절성 확인
ㄴ 엔티티,속성,관계를 어떻게 표현할지 정한 문서

6. 데이터 모델링이 충분하고 적절하게 수행되었는지 확인
- 논리 데이터 모델의 개념 완전성 및 정확성 확인
- 무결성이 보장이 되었는지 확인
- 엔티티간 실제 업무 규칙과 맞는지 확인
- 모델 관련 산출물 작성의 적합성 및 일관성에 대해 확인

7. 엔티티 및 프로세스 간의 연관 관계가 명확한지 확인
- 엔티티와 프로세스간 연관관계를 CRUD 매트릭스를 통해 확인

8. 데이터에 대한 접근 권한 및 통제가 명확히 분석되었는지 확인
- 데이터 중요도 및 데이터 암호화 가이드라인 확인

물리 데이터모델 설계
- 논리모델을 적용하고자 하는 기술에 맞도록 상세화해가는 과정

반정규화
- 정규화를 조금 포기하고, 조회성능을 높이기 위해 데이터를 중복하거나 테이블 구조를 바꾸는 설계 방법

반정규화를 하는 이유
- 데이터가 적을 때는 괜찮지만, 데이터가 많아지면 조회 성능이 느려질 수 있다.
- 그래서 자주 조회하는 데이터는 일부러 합치거나 중복해서 저장한다.

반정규화의 종류
중복테이블 추가하기
- 집계 테이블 추가

테이블 조합
- 항상 같이 사용되는 두 개 이상의 테이블을 하나로 합치는 것

테이블 분할
- 수직 분할
- 수평 분할

테이블 삭제
- 테이블 재정의나 칼럼의 중복화로 더 이상 사용되지 않는 테이블이 발생할 경우 삭제한다.

컬럼 중복
- 필요한 해당 테이블이나 컬럼을 중복하여 추가한다.

- 항상 같이 쓰는 테이블을 하나로 합친다.

장점
- join 없이도 바로 조회 가능

단점
- 회원 이름이 변경되면 주문 테이블의 회원 이름도 같이 수정해야 한다.

실제로 인덱스는 별도의 정렬된 자료구조로 저장이 된다.

지나치게 많은 인덱스는 오버헤드가 된다.
오버헤드 : 추가 부담
- 인덱스가 많으면 조회는 빨라지지만, 변경작업은 느리다.

예를 들어 회원 1명을 추가할때 테이블에만 저장하는 것이 아니라 여러 인덱스도 함께 갱신해야하기 때문이다.

인덱스는 추가 저장공간이 필요하다
- 테이블과 별도로 저장되는 검색구조이다.
- 인덱스를 만들면 저장공간을 추가로 사용한다.
- 그래서 무조건 많이 만드는 것은 좋지 않다.

넓은 범위를 인덱스로 처리하면 오히려 느릴 수 있다.
- 인덱스는 적은 데이터를 빠르게 찾을 때 효과적이다.
- 하지만 전체 데이터의 많은 부분을 조회하면 오히려 전체 테이블을 읽는 것이 더 빠를 수 있다.

인덱스와 테이블 데이터의 저장 공간을 적절히 분리한다.
- 대규모 DB에서는 테이블 데이터와 인덱스 데이터를 물리적으로 분리해서 저장하기도 한다.
- 이렇게 하면 디스크 입출력 성능이나 관리측면에서 유리할 수 있다.

뷰(View)
- 실제 데이터를 저장하는 테이블이 아니라, SELECT문을 저장해 둔 가상의 테이블
- 자주 사용하는 조회 SQL에 이름을 붙여둔 것

뷰가 필요한 이유
- 복잡한 SQL을 단순하게 사용 가능
ㄴ 여러 테이블을 JOIN하는 SQL은 길고 복잡하다.

- 특정 컬럼만 보여줄 수 있다.
ㄴ 개인정보, 급여와 같은 민감한 정보는 제외하여 뷰를 만들면 필요한 컬럼만 공개할 수 있다.

뷰 속성
REPLACE
- 뷰가 이미 존재하는 경우, 기존 뷰를 새 내용으로 다시 생성하는 속성

FORCE
- 기본 테이블이 존재하지 않아도 뷰를 생성하는 속성

NOFORCE
- 기본 테이블이 존재할 때만 뷰를 생성하는 속성
- Oracle에서 기본값은 보통 NOFORCE이다.
- 일반적으로는 참조할 테이블이 있어야 뷰를 만들 수 있다.

WITH CHECK OPTION
- 뷰의 조건을 만족하는 행만 INSERT 또는 UPDATE 할 수 있도록 제한하는 속성

- 활성 회원만 저장하는 VIEW
CREATE VIEW active_member_view as
select member_id, name, status
from member
where status = 'active'
WITH CHECK OPTION

가능한 수정
UPDATE active_member_view
set name = '김영희'
where member_id = 1;

- 이 뷰의 조건을 벗어나는 수정은 허용하지 않는다.

WITH READ ONLY
읽기 전용으로 작성된 뷰

뷰 설계 시 고려 사항
뷰는 결국 테이블을 조회한다.
- 실제 데이터를 저장하지 않는다.
- 실제로는 내부에서 원본 테이블의 SELECT가 실행되는 것과 같다.
- 그래서 뷰를 사용한다고 해서 무조건 빨라지는 것은 아니다.
- 오히려 뷰 안의 SQL이 복잡하면 성능 문제가 생길 수 있다.

복잡한 뷰는 성능이 느려질 수 있다.
- member,orders 테이블을 조인하는 쿼리문을 view로 만든다.
- 뷰를 조회하게 되면 실제로는 member와 orders 테이블을 조인하고 집계한다.
- 데이터가 많으면 이 작업은 느려질 수 있다.

뷰 안의 select 조건도 인덱스를 고려해야 한다.
- 뷰 안에 조건이 있다면, 해당 조건 컬럼에 인덱스가 있는지 확인해야 한다.
CREATE VIEW active_member_view as
select member_id, name, email
from member
where status = 'active'
- 이 뷰는 status 조건을 사용한다.
- 따라서 status 컬럼이 자주 조회되고 분포도가 적절하다면 인덱스를 고려할 수 있다.
- 다만 status같이 ACTIVE와 INACTIVE처럼 종류가 적고 대부분이 ACTIVE라면 인덱스 효과가 낮을 수 있다.

뷰를 사용하는 SQL의 WHERE절도 중요하다
- 뷰 안의 조건이 부족하더라도, 뷰를 조회하는 SQL에서 좋은 조건을 줄 수 있다.
CREATE VIEW order_view as
SELECT order_id,member_id,order_date,total_price
from orders;
- 모든 주문을 보여주는 뷰
- 그런데 실제 조회할 때는 다음처럼 조건을 준다.
SELECT * FROM order_view
WHERE member_id = 10;
- 이 경우 실제로는 orders.member_id를 조건으로 조회하게 된다.
- 따라서 orders.member_id에 인덱스가 있으면 성능이 좋아질 수 있다.

파티션
- 큰 테이블을 여러 개의 작은 영역으로 나누어 저장하는 방법

파티션 설계
- 큰 테이블을 여러 개의 작은 영역으로 나누어 저장하는 방법
- 주문 데이터가 1억건 있다고 가정을 하면
orders 테이블
주문번호
회원번호
주문일자
상품명
가격

만약 모든 데이터를 하나의 테이블에 저장하면 검색할 때 DB가 엄청난 데이터를 확인해야 한다.
- 시간이 오래 걸리기 때문에 데이터를 나눈다.

파티션이 필요한 이유
- 대용량 시스템에서는 데이터가 계속 증가한다.
- 데이터가 많아지면
조회속도 저하
백업 시간 증가
복구 시간 증가
디스크 사용량 증가

파티션 종류
1. 범위 분할
- 지정한 컬럼 값의 범위를 기준으로 데이터를 나누는 방법
주문테이블의 데이터를 주문일자를 기준으로 나눈다
주문 테이블
주문번호	주문일
101		2024-01-10
102		2025-03-01
103		2026-06-12

반정규화 분할 -> 테이블을 진짜로 여러개로 만듦
파티션 -> 하나의 테이블 내부에서 저장 영역을 나눈다.

CREATE TABLE orders(
	order_id INT,
	order_date DATE
)
PARTITION BY RANGE(YEAR(order_date))
(
	PARTITION p2024 VALUES LESS THEN (2025),
	PARTITION p2025 VALUES LESS THEN (2026),
	PARTITION p2026 VALUES LESS THEN (2027)
);

파티션을 만들어도 사용자는 일반 테이블처럼 사용한다.
- 원래 하던 것처럼 CRUD 작업을 한다.

주문데이터,로그데이터,게시글데이터,이력데이터
- 시간 기준 데이터에 많이 사용한다.
