요구사항 확인

1. 현행 시스템의 분석
- 새 시스템을 만들거나, 기존 시스템을 개선하기 위해 현재 사용중인 업무 방식, 프로그램,
데이터, 서버, 네트워크, 문제점 등을 조사하고 정리하는 활동

목적
- 새로운 시스템을 정확하게 만들기 위해 현재 상황을 이해한다.

문제점
1. 기존 업무의 흐름을 모른다면 필요한 기능을 빠뜨릴 수 있다.
2. 기존 데이터 구조를 모른다면 데이터 이전 시 오류 발생
3. 기존 시스템 연동을 모른다면 외부 시스템과 연결 실패
4. 사용자 불편 사항을 모른다면 새 시스템을 만들어도 만족도가 낮다.
5. 현재 원인을 모른다면 문제 해결이 아닌 단순 재개발이 된다.

현행 시스템 파악 절차
1단계 : 현행 시스템의 구성, 기능, 인터페이스 현황 파악
- 현재 시스템이 무엇으로 구성되어 있고, 어떤 기능을 제공하고, 다른 시스템과 어떻게 연결되어있는지 파악

시스템 구성현황 파악
- 현재 운영중인 시스템의 종류와 역할을 파악하는 것
ex)
시스템명 - 주요 사용자 - 역할
수강생 관리 시스템 - 관리자 - 수강생 등록,수정,조회
출결 관리 시스템 - 강사,관리자 - 출결 관리
상담관리 시스템 - 관리자 - 상담 이력 기록
결제 관리 시스템 - 관리자 - 수강료 결제 내역 관리
문자 발송 시스템 - 관리자 - 공지 문자 발송

기능 현황 파악
- 각 시스템이 제공하는 기능을 정리하는 것

수강생 관리 시스템
수강생 등록 : 신규 수강생을 등록
수강생 조회 : 학원에 다니는 수강생을 조회
수강생 수정 : 수강생의 정보를 수정
수강생 삭제 : 수강생의 정보를 삭제

인터페이스 현황 파악
- 시스템과 시스템이 데이터를 주고받는 연결 지점을 의미
- ex 결제 쇼핑몰
결제 API -> 주문번호, 결제금액, 결제 상태
택배사 API -> 주문번호, 주소, 송장번호
문자 발송 API -> 전화번호,메시지내용
이메일 API -> 이메일 주소, 인증 코드

- 현재 시스템이 어떤 구조로 만들어져있고, 어떤 소프트웨어를 사용하고 있는지 파악

선정 시 고려사항
1. 신뢰도
- 장기간 시스템을 운영할때 고장이 안나는가
- 특정 프로그램의 메모리 누수로 인한 성능저하가 없는가
- 운영체제상 보안상 허점으로 반복적인 패치 설치를 위한 재기동
- 운영체제의 버그 등으로 인한 패치 설치를 위한 재기동
2. 성능
- 대규모 동시 사용자 처리를 안정적으로 할 수 있는가
- 대규모 파일 작업 처리가 가능한가
- 지원 가능한 메모리 크기(32bit,64bit)
3. 기술지원
- 공급 벤더들의 안정적인 기술지원(문제가 생겼을때 도움을 잘 주는가)
- 다수의 사용자들 간의 정보 공유
- 오픈소스 여부(가격이 저렴)
4. 주변 기기
- 설치 가능한 하드웨어
- 다수의 주변기기 지원 여부(프린터,스캐너,usb,그래픽카드)
5. 구축비용
- 지원 가능한 하드웨어 비용(cpu 요구사항, 메모리 요구사항, 저장장치 요구사항)
- 설치할 응용 프로그램의 라이선스 정책 및 비용(운영체제 위에 설치할 프로그램들의 비용)

- 고객이 원하는 방향이 맞는지도 중요하나, 그 요구사항이 문서로 정확하고 일관성있게 정리되어있어야 한다.

요구사항 확인 기법
작성된 요구사항이 올바른지, 빠진 것은 없는지, 고객이 원하는 내용이 맞는지 확인하는 기법

1. 요구사항 검토
- 여러 사람이 모여 요구사항 문서를 읽고 문제를 찾는다.
오타, 잘못된 가정, 애매한 표현, 누락, 모순, 표준위반점을 찾는다.
- 검토자 그룹을 어떻게 구성하느냐가 중요하다.
예를 들어 고객 중심 프로젝트에서는 검토자 그룹에 고객 대표자가 1명 이상 포함되어야 한다.
- 검토는 시스템 정의서, 시스템 사양서, 소프트웨어 요구사항명세서를 완성한 시점에서 이루어진다.

시스템 정의서
- 무엇을 만드는지 큰 방향을 정의하는 문서(주요 기능만 정의)

시스템 사양서
- 정의서보다 조금 더 구체적인 문서(그 기능들이 어떻게 동작할 것인지)

소프트웨어 요구사항 명세서
- 개발자가 실제 구현할 수 있을 정도로 상세하게 적은 문서

2. 프로토타이핑(Prototyping)
- 최종 제품을 만들기 전에 일부 기능이나 화면을 미리 만들어 사용자가 확인하도록 하는 방법
- 소프트웨어 요구사항에 대해 소프트웨어 엔지니어가 해석한 것을 확인할 수 있다.
- 처음에는 생각하지 못했던 새로운 요구사항을 도출할 수 있다.

장점
- 분석가의 가정을 파악하고 잘못된 경우 유용한 피드백을 제공한다.
- 사용자 인터페이스의 동적인 행위가 문서나 그래픽 모델보다 프로토타입으로 이해하기 쉽다. 
- 요구사항의 가변성이 프로토타이핑 이후에 급격히 감소한다.
- 잘못된 요구사항에 대해 자원 낭비 방지

단점
- 핵심 기능보다 디자인 집중하게 될 수 있다.
- 프로토타입을 만드는 시간과 비용이 추가로 발생할 수 있다.

프로토타이핑 종류
- 종이에 그림 : 가장 단순함

화면 프로토타입
- Figma와 같은 도구 사용

기능 프로토타입
- 일부 기능을 실제로 구현

모델 검증
- 개발 전에 만든 분석 모델이 올바르게 작성되었는지 확인하는 방법
- 개발 전에 모델 오류를 찾기 위해서 검증을 해야된다.
- 예를 들어 객체 모델의 경우 객체들 사이에 존재하는 의사소통 경로를 검증하기 위해 
정적 분석을 수행하는 것이 유용하다.

모델 : 실제 프로그램 코드가 아니라, 개발 전에 만드는 분석용 설계 자료

모델의 종류 
업무 흐름도 : 사용자가 어떤 순서로 업무를 처리하는지 나타내는 그림
유스케이스 다이어그램 : 사용자가 시스템으로 무엇을 할 수 있는지 나타낸 그림
객체 모델 : 시스템 안에 어떤 객체들이 있고 서로 어떻게 연결되는지 나타낸 모델
클래스 다이어그램 : 클래스, 속성, 메서드, 관계를 표현한 그림
데이터 모델 : 데이터베이스에 어떤 데이터가 저장되는지 나타낸 모델

의사소통 경로
- 객체들끼리 정보를 주고받을 수 있는 연결 관계
예 : 도서 대여 시스템에서 회원이 도서를 빌려면 다음과 같이 동작해야 한다.
회원 -> 대여 -> 도서

회원이 대여를 요청하고, 대여 객체는 도서 객체에게 재고나 대여 가능 여부를 확인해야 한다.
이때 대여와 도서 사이에 연결이 없다면 문제가 생긴다.

정적분석
- 프로그램을 직접 실행하는 것이 아닌, 구조만 보고 검사하는 방식
- 객체 모델을 실행할 수는 없지만, 그림이나 관계를 보고 구조적으로 검사하는 것

개발이 거의 끝난 후 만든 프로그램이 고객이 요구한 내용을 정말 만족하는지 최종 확인하는 테스트
- 요구사항의 중요한 속성은 최종 제품이 요구사항을 만족시키는 기능인지 확인이 가능해야 한다.
- 각각의 요구사항을 어떻게 확인할 것인지에 대한 계획을 세워야 한다.

- 요구사항 반영의 확인 : 모델에 제대로 반영되었는지 확인
- 누락 발견 : 필요한 객체, 테이블, 관계 흐름이 빠졌는지 확인
- 오류 발견 : 잘못된 관계나 잘못된 흐름을 찾음
- 일관성 확인 : 여러 모델이 서로 맞는지 확인
- 구현가능성 확인 : 실제 코드와 DB로 만들 수 있는지 확인
- 테스트 가능성 확인 : 나중에 테스트할 수 있는 구조인지 확인

4. 인수 테스트
- 개발이 거의 끝난 후 만든 프로그램이 고객이 요구한 내용을 정말 만족하는지 최종 확인하는 테스트
- 코드의 동작 여부보다 고객의 요구사항 충족이 더 중요하다.
과정
요구사항 작성 -> 인수테스트 계획 작성 -> 개발 진행 -> 시스템 완성 -> 인수 테스트 수행 -> 승인 또는 수정

종류
사용자 인수 테스트
운영 인수 테스트
계약 인수 테스트
규정 인수 테스트
알파 테스트
베타 테스트
