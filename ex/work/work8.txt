[문제 3] 
다음은 공유 풀(Shared Pool)과 데이터베이스 버퍼 캐시(Data Buffer Cache)에 대한 설명입니다. 대량의 회원을 조회하는 동일한 SQL문이 반복해서 실행될 때, 두 메모리 영역이 SQL 처리 흐름(구문 분석, 실행, 추출) 단계에서 각각 성능 최적화에 어떻게 기여하는지 메커니즘을 비교하여 서술하시오.

공유풀
- 이전에 실행된 sql문과 실행 계획을 임시 보관하므로, 동일한 SQL이 들어왔을 때 문법 검사, 오브젝트 확인, 실행 계획 수립 등의
작업을 생략한다.

버퍼캐시
- 디스크에서 한번 읽어온 데이터를 메모리에 유지하므로, 동일한 데이터 조회 시 느린 디스크 파일 I/O를 발생시키지 않고
메모리에서 바로 데이터를 읽어와 수행 속도를 극적으로 향상시킨다.

[문제 4] 
APM 리소스 모니터링 화면에서는 CPU 20%, 메모리 40%로 매우 정상적인 수치를 보이고 있으나, 실제 사용자는 "주문 완료 화면이 넘어가는 데 8초 이상 걸린다"며 불편을 겪고 있습니다. 이 현상이 발생할 수 있는 원인을 엔드투엔드(E2E) 모니터링 관점에서 분석하고, 성능 개선을 위해 개발자가 확인해야 할 내부 유틸리티 2가지를 제시하시오.

원인 분석
- 리소스는 여유가 있으나 주문 처리 트랜잭션 내부에서 병목 발생
- E2E 관점에서 볼때 외부 결제 API 호출 응답 지연, 문자 발송 서버의 지연, 혹은 특정 SQL의 락(LOCK)이나 비효율적인 실행 계획으로
인해 내부 프로세스가 대기 상태에 빠졌을 가능성이 높다.

확인해야 할 유틸리티
- SQL 내부의 자원 소모량과 실행 시간을 상세히 분석하는 TKPROK과 해당 SQL이 인덱스를 타지 못하고 전체 테이블 스캔을 하는지 내부 길찾기 경로를 확인하는 EXPLAIN PLAN을 활용해야 한다.
