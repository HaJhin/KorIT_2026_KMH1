계층 구조
Presentaiton Layer(표현 계층) : Controller
- HTTP 요청 받기
- 요청 데이터 검증
- Service 호출
- HTTP 응답 반환

Business Layer(비즈니스 계층) : Service
- 실제 업무 로직을 처리하는 계층이다.

Persistance Layer(영속 계층) : Repository
- 데이터베이스에 접근하는 계층
- 데이터 저장,조회,수정,삭제

@RequestMapping("리소스")
- HTTP 요청(URL)을 특정 클래스나 메서드와 연결하는 어노테이션이다.

http://localhost:8080/test -> 스프링은 "이 요청을 어떤 메서드가 처리해야하지?"

@RequestMapping("test")
public class TestController{...}

/test로 시작하는 요청은 모두 TestController가 처리한다.

@GetMapping("경로") 
Get으로 들어오는 요청을 받아서 처리하겠다.

@PathVariable
경로의 일부를 변수로 만들어서 매개변수에 데이터를 넣어주는 어노테이션
경로 변수와 매개변수의 이름이 같으면 생략 가능
- 리소스 자체를 식별할 때 사용
/users/10 -> 10번 회원 -> select * from member where id = 10;
/products/5 -> 5번 상품
/orders/20 -> 20번 주문

@RequestParam

프로토콜://도메인/경로(리소스)?쿼리스트링

REST API
REST(Representitaional State Transfer)아키텍쳐를 기반으로 하는 API이다.
클라이언트와 서버 간의 상호작용을 HTTP 프로토콜을 사용해 설계한 웹 서비스의 인터페이스로, 데이터를 쉽게 주고받을 수 있게 해준다.
웹 어플리케이션, 모바일 앱, 마이크로서비스 등 다양한 시스템 간의 통신을 위한 표준으로 널리 사용된다.
-REST 아키텍쳐 스타일은 6가지 제약조건으로 구성된다.
- 이 가이드를 따르는 API를 RESTful API라고 한다.

REST API의 주요 개념
클라이언트 - 서버
리소스를 관리하는 서버가 존재하고, 다수의 클라이언트가 리소스를 소비하기 위해 네트워크를 통해 서버에 접근하는 구조

상태가 없는(stateless)
클라이언트가 서벙 요청할 때, 이전 요청의 영향을 받지 않는다.
/login을 통해서 로그인하고 /page로 이동할 때 서버는 로그인 사실을 모른다.
그렇기 때문에 로그인 상태를 유지하려면 다른 요청을 보낼때마다 로그인했다는 증명을 같이 보내야 한다.

http 메서드 사용의 일관성
GET : 리소스를 조회할 때 사용
POST : 새로운 리소스를 생성할 때 사용
PUT : 기존 리소스를 업데이트할 때 사용
DELETE : 리소스를 삭제할 때 사용

GET /users -> 모든 사용자 조회
GET /users/{id} -> 특정 사용자 조회
POST /users -> 새로운 사용자 생성
PUT /users/{id} -> 사용자 정보 업데이트
DELETE /users/{id} -> 사용자 정보 삭제

GET /posts -> 모든 게시물 조회
GET /posts/{id} -> 특정 게시물 조회
POST /posts -> 새로운 게시물 생성
PUT /posts/{id} -> 게시물 업데이트
DELETE /posts/{id} -> 게시물 삭제

URL 구조의 일관성
- 경로를 일관되게 설계하는 것도 중요하다.
- 리소스의 이름은 복수형으로 일관되게 사용하고, 리소스간 관계를 표현할 때도 규칙적으로 작성해야 한다.

GET /users/{userId}/posts
POST /users/{userId}/posts
GET /users/{userId}/posts/{postId}

동일 출처 정책(Same-Origin Policy)
- 브라우저는 기본적으로 보안을 위해 동일 출처 정책이라는 규칙을 따른다.
- 같은 출처에서 로드된 웹사이트만 서로 데이터를 주고받을 수있다.
- 다른 출처에서 데이터를 요청하는 것을 제한하는 정책
- 이 정책은 보안을 위해 존재하는데, 악의적인 웹사이트가 사용자의 브라우저를 이용해 다른 출처에서 데이터를 가져오지 못하게
막는 역할을 한다.

데이터베이스를 프로젝트에서 매우 편리하게 사용할 수 있게 해주는 기술

JDVC만 사용해서 연결할 경우
- 개발자가 직접해야하는 일들이 너무 많다
- 연결, 쿼리문도 직접 작성해야 한다. SQL 실행, 결과 받아서 JAVA 객체로 변환, 연결 종료

ORM(Object Relation Mapping)
객체와 관계를 매핑(1:1로 연결)

Java는 데이터를 객체로 다룬다.
DB는 데이터를 테이블로 관리

JPA가 이 둘을 연결
- 내부적으로 SQL을 실행한다
- 개발자가 SQL을 직접 작성하지 않고 객체 중심으로 데이터를 처리할 수 있다.

Entity
- 테이블이라 1대1로 매핑되는 클래스
- 테이블이 없으면 jpa 설정으로 자동으로 테이블을 만들어준다.
ex) TodoEntity -> todo_entity라는 이름으로 테이블을 만들어준다.
@Entity : 이 클래스는 JPA가 관리하는 데이터베이스 Entity라고 선언
@Table(name=테이블명) : 테이블 이름을 명확하게 지정하고 싶으면 사용하는 어노테이션

@Id : 해당 필드를 기본키(PK)로 설정
@GeneratedValue(strategy = GenerationType.IDENTITY) : 1부터 순차적으로 대입
@Column() : 컬럼의 세부 설정
- name : 컬럼의 이름
- nullable : NULL 허용 여부
- unique : UNIQUE 제약 조건
- length : 문자열의 길이

@CreationTimeStamp : Hibernate에서 제공하는 어노테이션으로 데이터 생성 시간을 자동으로 저장
private LocalDateTime createAt;

@UpdateTimeStamp : Update 쿼리가 실행될 때 시간을 저장해준다.
private LocalDateTime updatedAt;

영속계층에서 메서드를 이용해서 CRUD 작업을 한다.

JPA에서 기본적으로 제공하는 메서드를 사용하기 위해서는 JpaRepository<T,ID>인터페이스를 상속받아야한다.

T : 엔티티 클래스
ID : PK의 타입

기본적으로 제공해주는 메서드
save() : 추가나 업데이트할 때 사용
findById() : 기본키를 통해서 데이터 하나를 조회, 반환형이 Optional이다!!
findAll() : Entity의 모든 데이터를 조회
deleteById() : 기본키 ID를 기준으로 데이터를 삭제한다.
count() : 해당 Entity의 전체 데이터 개수를 반환
existsById() : 특정 ID의 데이터가 존재하는지 확인 

쿼리메서드 작성방법
메서드 이름을 규칙에 맞게 작성하면 Spring Data JPA가 쿼리를 자동 생성합니다.

동작 + By + 조건
List<T> findByTitle(String title) : 제목을 조건으로 데이터를 찾는다.

fintBtTitleContaining(String keyword) : 제목에서 keyword를 포함하는 데이터 찾기

두개의 조건
findByUserIdAndDone(String userId, boolean done)

findByUseridOrTitle(String userId, String title)

특정 문자열로 시작
findByTitleStartingWith(String str)

특정 문자열로 끝
findByTitleEndingWith(String str)

범위
초과
findByAgeGreaterThan(int age)

미만
findByAgeLessThan(int age)

findByAgeBetween(int StartAge, int endAge)

정렬
findByUserIdOrderByAsc(String userId)

findByUserIdOrderByTitleAsc(String userId)
