논리데이터 모델의 구성 요소 중 데이터베이스에 명시된 규정에 따라 릴레이션이 가질 수 있는 유효한 데이터 값의 범위를 제약하는 규칙을 의미하는 용어를 작성

제약조건

//

관계 데이터베이스 모델에서 상위 테이블의 기본키(Primary Key)를 참조하여 테이블 간의 연결 고리 역할을 하는 속성을 무엇이라고 하는지 작성

외래키(Foreign Key) 속성

//

데이터베이스에서 발생할 수 있는 이상 현상의 3가지 종류와 개념

삽입 이상
데이터를 삽입하는 과정에서 불필요한 정보도 입력하게 되거나 아예 삽입을 못하는 것

갱신 이상
데이터를 갱신하는 과정에서 일부만 갱신되어 데이터의 불일치가 발생하는 것

삭제 이상
데이터를 삭제하는 과정에서 필요한 데이터까지 연쇄삭제하게 되는 것

//

DB 설계 과정에서 개체 무결성과 참조 무결성은 데이터의 정확성을 보장하는 핵심규칙이다.
이 두 제약 조건의 개념과 위배되지 않기 위한 세부 규칙을 비교하여 서술

개체 무결성 : 각 행은 구분할 수 있어야하며, 기본키는 중복이 되어서도, NULL 값이어서도 안된다.
참조 무결성 : 다른 테이블을 참조할 때 존재하는 데이터만 참조해야 한다.

//

제1정규형 : 모든 테이블이 원자값이어야 한다.
제2정규형 : 기본 키가 아닌 모든 속성이 기본키에 완전 함수적 종속을 만족해야 한다.
제3정규형 : 기본 키가 아닌 모든 속성이 기본키에 이행 함수정 종속을 만족하지 않아야 한다.

//

관계형 데이터 모델에서 릴레이션의 행을 뜻하는 용어, 카디널리티의 수와 직결되는 이것은?
- 튜플

어떤 릴레이션 R에서 속성 X의 값 각각에 대해 속성 Y의 값이 오직 하나만 연관되어 있을 때 Y는 X에 이것 되어 있다고 한다.
- 함수적 종속성

개념적 데이터 모델링 단계에서 도출된 ERD를 관계형 DB의 논리적 테이블 구조로 변환하는 과정을
릴레이션 스키마 변환이라고 한다.
이 과정에서 1:N 관계를 가진 두 개체가 테이블로 변환될 때 외래키가 지정되는 규칙 서술

1 : N 관계에서 외래키는 항상 N쪽에 해당하는 자식 테이블에 생성된다.

1쪽 테이블의 기본키(PK)값을 가져와서 N쪽 테이블의 외래키 속성으로 추가하여 두 테이블 간의 연결고리를 형성한다.

//

DB의 정규화 과정은 데이터 무결성을 높여주지만 과도한 정규화는 시스템의 성능 저하를 유발한다.
정규화가 조회 성능을 떨어뜨리는 이유를 연산의 관점에서 서술

- 정규화 과정이 진행될수록 한 테이블을 다수의 테이블로 나누게 되고, 그 과정에서 필요 이상의 조인 및 불필요하게 많은 테이블을 조회하게 되며 시스템의 성능 저하를 유발하게 된다.

//

제2정규형의 정의를 설명하고, 테이블이 제2정규형을 만족하지 못할때 생기는 문제점을 복합키 관점에서 서술

1정규형을 만족하고 기본키가 아닌 모든 속성이 기본키에 완전 함수성 종속을 이루어야 하는 것을 제2정규형이라고 한다.
기본키가 복합키로 구성되어 있을때, 데이터에 부분 함수성 종속이 남아있으면 데이터를 조회 시 데이터의 중복이 생기고, 이로 인해 이상현상이 발생한다.

//

데이터 무결성 제약 조건 중 도메인 무결성의 개념 서술, DB 시스템 상에서 구현하거나 검증할 수 있는 구체적인 방법 2가지 서술

도메인 무결성
- 특정 속성 값이 그 속성에 정의된 유일한 도메인에 속한 값이어야 한다.
- NOT NULL, CHECK 등의 제약 조건을 지정. DEFAULT를 통해 기본값을 지정 등이 있다.

//

데이터 접근 속성을 향상시키기 위해 정규화된 데이터 모델을 의도적으로 중복,통합,분리시키는 기법

- 반정규화

//

대용량 테이블을 작은 논리적 단위로 나누어 관리함으로서 성능을 향상 시키는 기법으로,
범위, 해시, 목록 등이 있는 이 기술

- 파티션 분할 기법(파티셔닝)

//

물리적 설계 단계에서 데이터 무결성을 보장하기 위해 테이블 내 특정 컬럼에 비어있는 값(NULL)이 들어오지 못하도록 강제하는 제약조건의 명칭

- NOT NULL

//

논리적 데이터 모델을 물리적 데이터 모델로 변환할 때, 시스템의 성능 향상을 위해 테이블 수평 분할을 수행하는 기준과 이로 인해 얻을 수 있는 장점을 데이터 검색 속도 관점에서 서술

- 특정 범위 별 빈도 차이가 많을때, 해당 범위 별로 수평 분할을 진행한다.
이로 인해 특정 범위의 데이터만을 빠르게 조회 및 수정, 삭제가 가능하다.

//

물리 데이터저장소 설계 시 반정규화를 수행하면 데이터 조회성능은 향상되지만 반대로 시스템 측면에서 감수해야하는 부작용을
데이터 수정 및 무결성 관점에서 서술

- 데이터의 중복과 통합 과정이 이루어지며, 그 과정에서 데이터를 수정 시 중복된 모든 곳을 찾아 수정해야 하므로 성능 오버헤드가 증가한다.
만약 일부 테이블만 반영되고 누락될 경우 데이터의 불일치가 발생하며 데이터 무결성이 깨지고 이상현상이 발생한다.

//

대규모 트랜잭션이 발생하는 시스템에서 중복 테이블을 추가하는 반정규화 기법인 '집계 테이블 추가'와 '진행 테이블 추가'의 개념적 차이 서술

집계 테이블 추가 
대량의 과거 이력 데이터를 기반으로 정기적인 합계, 평균 등의 연산을 미리 수행하여 그 결과를 별도 테이블에 저장해두는 방식

진행 테이블 추가
여러 단계의 업무 프로세스(예 : 주문 -> 결제 -> 배송) 중 현재 진행 중인 상태나 최신 트랜잭션 데이터만을 별도로 분리하여 빠른 조회가 가능하도록 관리하는 방식

//

물리적 저장 장치 설계 시 고려해야 하는 '공간 효율성'과 '접근 속도(Access Time)' 간의 상충 관계에 대해 간략히 서술하시오.

접근 속도를 높이기 위해 인덱스를 대량으로 추가하거나 반정규화를 통해 테이블 중복 저장을 하게 되면 데이터를 빠르게 찾을 수는 있지만 추가적인 물리 공간을 많이 소모하여 공간 효율이 떨어진다.
반대로 물리 공간을 최소화 하기 위해 극단적인 정규화를 수행하게 되면 공간 효율성은 극대화 되지만, 빈번한 조인 연산과 디스크 탐색으로 접근 속도는 느려진다.

//

DB의 성능을 최적화하기 위해 데이터가 저장되는 물리적 공간이자, 테이블과 인덱스가 실제로 할당되는 단위인 이것의 명칭

- 테이블 스페이스

//

DB 오브젝트 중 하나로 물리적 테이블에 링크되어 보안성을 높이고 복잡한 쿼리를 단순화 해주는 가상의 테이블

- 뷰 (VIEW)

//

인덱스를 무분별하게 많이 생성했을때 데이터 삽입 연산의 성능이 저하되는 이유

- 데이터를 삽입 시 컬럼마다 생성된 인덱스도 삽입하기 때문에, 인덱스가 많아질 수록 삽입되는 인덱스의 양도 증가한다.
즉 과도한 삽입 연산이 발생하며 성능이 저하된다.

= 새로운 데이터를 테이블에 삽입할때 테이블에 할당된 모든 인덱스 구조에도 해당 데이터의 키값과 주소를 추가해야 한다.
인덱스 블록에 자리가 부족하면 블록 분할 현상이 발생하고, 인덱스 정렬 구조를 실시간으로 재정렬해야하므로 무분별한 인덱스 디스크 I/O 작업을 가중시켜 데이터 삽입 성능을 급격히 떨어뜨린다.

//

뷰의 특징 중 독립성과 보안성에 대해 실제 개발 환경의 예시를 들어 서술

보안성 : 급여 테이블에서 주민번호나 계좌번호같은 민감한 컬럼을 제외하고 이름과 직급만 조회하는 뷰를 생성해 일반 직원에게 권한을 부여함으로서 민감 정보 노출을 차단할 수 있다.

독립성 : 물리적 원본 테이블의 구조가 변경되더라도 외부 어플리케이션은 기존 구조에 맞춰 선언된 뷰를 계속 호출하므로,
어플리케이션 소스 코드를 수정하지 않아도 된다.

//

DB 오브젝트 중 시퀀스의 역할과 물리 DB 구성시 왜 시퀀스를 사용하는지 그 필요성을 서술

호출될 때마다 순차적으로 증가하는 순번을 발행해주는 오브젝트이다.
주로 기본키 값을 중복없이 자동으로 생성할때 사용한다.

물리 구성 시 동시 접속자가 많은 대규모 시스템에서 중복되지 않는 기본키 값을 얻기 위해
DBMS 자체에서 고속으로 독립적인 순번을 안전하게 발행하기 위해 사용한다.

//

SQL 문장을 블록화하여 복잡한 로직을 처리할 수 있게 해주는 절차형 SQL 종류 중 결과값을 반드시 반환해야하는 오브젝트
- FUNCTION

절차형 SQL 내에서 특정한 이벤트가 발생할때마다 연쇄적으로 자동실행되도록 정의된 오브젝트
- TRIGGER

프로시저 내에서 행 단위로 복수의 데이터 세트를 순차적으로 참조하고 제어하기 위해 사용하는 일종의 포인터 역할을 하는 오브젝트
- CURSOR

PL/SQL 등 절차형 언어에서 실행 중 발생할 수 있는 오류나 예외상황을 처리하기 위해 사용하는 선언부의 명칭
- EXCEPTION

프로시저 작성 시 외부에서 값을 입력받거나 실행 후 결과값을 외부로 내보내기 위해 선언하는 매개변수를 뜻하는 용어
- 파라미터

//

절차형 SQL인 저장 프로시저(Stored Procedure)를 사용하는 것이 일반적인 애플리케이션 내 단독 SQL(임베디드 SQL 등) 구문을 연속으로 실행하는 네트워크 트래픽 및 성능 측면에서 왜 유리한지 서술

- 단독 SQL 구문을 사용하면 매 연산마다 어플리케이션 서버와 DB서버 간에 요청과 결과를 주고받는 네트워크 트래픽이 빈번하게 발생한다.
반면 프로시저는 복잡한 로직과 여러 SQL을 DB 서버 내에 하나의 프로그램으로 미리 저장해두므로 단 한번의 프로시저 호출로 모든 로직을 DB 내부에서 처리하여 네트워크 부하를 극적으로 줄이고 성능을 향상시킨다.

//

트리거 내부에서 무분별하게 DML 연산을 수행하거나 트랜잭션 제어어(TCL)인 COMMIT 또는 ROLLBACK을 사용할 수 없는 물리적/논리적 이유를 서술

- 트리거는 특정 테이블의 DML 이벤트에 묶여 자신을 유발한 상위 트랜잭션의 일부로 물리 작동한다. 만약 트리거 내부에 COMMIT이나 ROLLBACK이 포함되면 상위 어플리케이션의 트랜잭션 전반을 강제로 확정/취소해버려 트랜잭션의 원자성과 무결성을 파괴하게 된다.

원자성 : 모두 성공하거나 모두 실패해야 하는 성질
무결성 : 데이터에 결함이 없고 완벽해야 하는 성질

//

프로시저 내부에 디버깅용 코드를 삽입하여 실행 중인 변수의 현재 값을 화면에 출력해주는 오라클 PL/SQL의 대표적인 빌트인 패키지 명칭
- DBMS_OUTPUT

//

데이터 조작 프로시저를 테스트할 때 실제 운영 중인 DB 환경에서 직접 테스트를 수행하면 안되는 이유와 이를 방지하기 위한 테이블 분리 및 데이터 격리 방안에 대해 서술

실제 운영 DB 환경에서 테스트를 수행하면 잘못된 로직이나 데이터 변경으로 인해 실제 고객 데이터가 임의로 수정/삭제되어
오염되거나 락(LOCK) 충돌로 인하여 운영 중인 서비스가 중단될 수 있다.

이를 방지하기 위해 개발자 전용 테스트 데이터베이스를 구축하고, 실제 운영 데이터를 복사한 더미 데이터를 활용해야 한다.

//

프로시저 테스트 중 무한 루프에 빠지는 현상이 발견되었다. 이 결함을 찾아내기 위해 소스 코드 상에서 검증해야하는 핵심 영역과 해결 방안 서술

- 프로시저 내부 반복문의 종료조건이 올바르게 설계되었는지 확인한다.

//

DBMS 내부에서 SQL 문을 어떻게 실행할지 결정하고 최적의 경로를 찾아주는 핵심 엔진의 명칭
- 옵티마이저

오라클 등에서 사용자가 SQL 문에 직접 최적화 경로를 유도하기 위해 작성하는 힌트 구문 중, 순차 검색 대신 특정 인덱스를 강제로 타게 만드는 힌트 지시어
- /*+ INDEX */

실행할 SQL 구문을 미리 파싱하고 컴파일하여 메모리에 올려둔 뒤, 파라미터만 바꾸어 재사용함으로서 최적화를 돕는 DBMS 내의 공유 메모리 영역
- 공유 풀 메모리 영역

프로시저 내부 쿼리문의 성능을 분석하기 위해 DBMS가 제공하는 SQL의 내부 연산 순서 및 자원 소모 비용 정보를 시각적으로 보여주는 것
- 실행 계획

프로시저 내부의 대량 데이터 처리 쿼리 성능을 파악하기 위해 활용하는 오라클의 대표적 유틸리티 두 가지인 TKPROF와 EXPLAIN PLAN의 차이점을 분석 성격 관점에서 비교 서술

- TKPROF : 실제로 실행된 SQL의 추적 파일을 가독성있게 변환하여, 실제 소모된 CPU 시간, 디스크 I/O 횟수, 처리 건수(Rows)등의 '실제 리소스 수행 통계 결과'를 사후 분석하는 도구

- EXPLAIN PLAN : SQL을 실제로 수행하지 않고 옵티마이저가 수립한 데이터 액세스 경로와 '수행 순서 계획표'만을 PLAN_TABLE에 저장하여 예측하는 도구

//

시스템이 갑자기 느려졌을때 서버 컴퓨터 자원을 모니터링 하는 리소스 모니터링 도구와 사용자의 거래를 끝까지 추적하는 E2E 모니터링 도구의 결정적인 진단 차이점을 비교 서술

- 리소스 모니터링은 CPU, 메모리, 디스크, 네트워크 상태 등 서버 자체의 하드웨어만 감시하므로 시스템 상태가 '모두 정상'인 것처럼 보여 문제의 원인을 잡지 못한다.
- 반면 E2E 모니터링 도구는 사용자의 요청부터 내부서버, DB 조회, 외부 API 호출까지의 트랜잭션 과정을 결합 추적하므로 실제 장애 원인을 명확히 찾아낼 수 있다.

//

테스트 결과와 정의된 요구사항을 기준으로 데이터 조작 프로시저의 성능 이슈를 해결하기 위한 '성능 개선 및 해결단계(6가지 핵심 방안)'을 순서대로 나열하기

1. 속도를 저하시키는 SQL 구문 재작성
2. 실행 계획 개선
3. 인덱스 재구성
4. 시스템 리소스 병목 구간 조정
5. 개선 후 동일한 테스트로 효과 검증
6. 성능 개선 결과 문서화 및 공유

//

데이터 조작 프로시저를 최적화할때 조건절 우변 리터럴 값을 직접 하드코디하지 않고 Where phone = :b1과 같이 작성하는 방식을 서술 이 방식을 적용하면 SQL이 최초 1회만 파싱되어 공유 풀에 저장되므로 시스템 전체의 CPU 자원을 크게 절약할 수 있다.

- 바인드 변수 작성 방식
소프트 파싱을 유도하여 DB의 CPU 자원을 아끼고 성능을 최적화하기 위함

//

데이터베이스 성능 모니터링 도구 중 시스템 전반의 자원 사용량을 중심으로 감시하는 인프라 모니터링과 대비되는 개념 작성
애플리케이션의 트랜잭션 시작부터 DB 질의 수행 및 응답까지의 전체 흐름을 추적하고 병목 구간을 시각화해주는 소프트웨어 성능 관리 솔루션의 약어이다

- APM

// 

절차형 SQL에서 실행 도중 발생할 수 있는 데이터 정합성 오류나 비즈니스 규칙 위배 상황을 처리하기 위해 시스템 에러가 아님에도
개발자가 직접 정의하여 발생시키는 예외 처리 방식의 명칭

-  사용자 정의 예외

//

명시된 시스템의 안정적 운영 지표 중 사용자가 필요할 때 시스템을 정상적으로 사용할 수 있는 정도를 뜻하는 용어
시스템이 장애나 점검 등으로 인해 정상적으로 서비스를 제공하지 못하는 시간을 뜻하는 핵심 용어 2가지를 차례로 작성

- 가용성, 다운타임

// 

사용자가 쿼리를 날렸을 떄 구문 분석 단계에서 공유 풀이 수행하는 핵심 역할과 만약 동일한 쿼리가 공유 풀에 존재할때 얻을 수 있는 성능적 이점을 하드 파싱의 생략 관점에서 서술

공유풀이 수행하는 역할 : 데이터베이스 메모리 내에서 이전에 실행된 SQL문과 최적의 경로 정보인 실행 계획을 임시로 보관하는
보관함 역할

성능적 이점 : 동일한 쿼리가 이미 공유 풀에 저장되어 있다면 옵티마이저가 문법 검사, 오브젝트 권한 확인, 실행 계획을 처음부터 다시생성할 필요가 없다. 구문 분석 속도가 많이 단축된다.

//

프로시저 내부의 SELECT 문이 실행될 때 서버 프로세스가 디스크가 아닌 메모리 영역인 데이터베이스 버퍼 캐시에서 데이터를 찾았을 때와 찾지 못했을 떄의 물리적 처리 과정의 차이점을 데이터 파일과 속도 관점에서 비교 서술

버퍼캐시에 데이터가 있을 때 : 버퍼 캐시에서 데이터를 즉시 읽어 클라이언트로 반환하므로 물리적 I/O 자원을 쓰지 않아서 처리 속도가 매우 빠르다.

버퍼캐시에 데이터가 없을 때 : 디스크에 실제 저장된 물리파일인 데이터 파일에서 관련된 테이블 블록을 직접 읽어와야 하므로
속도가 느리다. 이때 읽어온 데이터는 향후 재사용을 위해 다시 버퍼 캐시에 임시저장된다.
