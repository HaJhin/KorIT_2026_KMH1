화이트 박스 테스트
- 프로그램의 소스 코드, 내부 로직, 제어 흐름, 조건문. 반복문을 확인하면서 수행하는 테스트
- 테스트 담당자가 프로그램 내부 구조를 알고 있다는 전제에서 진행한다.

블랙 박스 테스트
- 프로그램의 내부 소스코드나 구조를 보지 않고 입력값을 넣었을 때 기대한 출력값이 나오는지 확인하는 테스트
- 사용자 요구사항에 따라 기능이 정확하게 동작하는지 확인

드라이버
- 상향식 테스트에서 아직 개발되지 않은 상위 모듈을 대신하여 하위 모듈을 호출하는 임시 프로그램

스텁
- 하향식 테스트를 수행할 때 아직 개발되지 않은 하위 모듈을 대신하는 임시 프로그램

1.
V 모델은 소프트웨어 개발 단계와 테스트 단계를 서로 대응시켜 개발과 테스트를 함께 계획하는 개발 모델이다.
- 각 개발 단계에서 만든 산출물이 올바르게 구현되었는지 대응되는 테스트를 통해 검증하기 때문이다.
요구분석 -> 인수 테스트
아키텍처 설계 -> 시스템 테스트
모듈 설계 -> 통합 테스트
구현 -> 단위 테스트

2.
단위 테스트
목적 : 하나의 기능이나 모듈이 정상적으로 동작하는지 확인한다
대상 : 메서드, 클래스, 서비스 등 작은 단위
수행자 : 개발자

통합 테스트
목적 : 모듈 간 연결과 인터페이스가 정상적으로 동작하는지 확인
대상 : 컨트롤러, 서비스, DAO 등의 연결
수행자 : 개발자 또는 테스트 담당자

시스템 테스트
목적 : 전체 시스템이 요구사항에 맞게 동작하는지 확인한다.
대상 : 전체 시스템
수행자 : 테스트 팀

인수 테스트
목적 : 실제 업무에 사용할 수 있는지 확인한다
대상 : 실제 업무 절차
수행자 : 사용자 또는 고객

4.
구조 기반 테스트
기준 : 프로그램 내부 구조
코드 확인 : 확인함
종류 : 화이트 박스 테스트
목적 : 제어 흐름과 조건 검증

명세 기반 테스트
기준 : 요구사항과 명세
코드 확인 : 확인하지 않음
종류 : 블랙박스 테스트
목적 : 입력과 출력 및 요구사항 검증

4.
상향식 : 하위 모듈부터 상위 모듈 방향으로 결합하여 테스트하는 방법
하향식 : 상위 모듈부터 하위 모듈 방향으로 결합하여 테스트하는 방법
Driver : 아직 개발되지 않은 상위 모듈을 대신하여 하위 모듈을 호출하는 임시 프로그램
Stub  : 아직 개발되지 않은 하위 모듈을 대신하여 미리 준비한 결과를 반환하는 임시 프로그램

5.
사용자 인수 테스트 
수행자 : 업무 담당자, 고객
확인 내용 : 업무 절차와 요구사항 충족 여부

운영상의 인수 테스트
수행자 : 시스템 운영자, 서버 관리자
확인 내용 : 백업, 복원, 장애 복구, 계정 관리

계약 인수 테스트
수행자 : 발주사와 개발사
확인 내용 : 계약서와 요구사항 충족 여부

규정 인수 테스트
수행자 : 품질 담당자, 감사 담당자
확인 내용 : 법규, 보안, 산업 표준 준수 여부

알파테스트
수행자 : 개발 조직 내부 직원
확인 내용 : 내부 환경에서 제품 품질 확인

베타테스트
수행자 : 실제 사용자
확인 내용 : 실제 환경에서 사용성 및 문제점 확인
