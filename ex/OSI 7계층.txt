세션 계층
- 컴퓨터끼리 연결을 만들고 유지하거나 끊는 역할
세션 설정
통신을 시작하기 전에 두 시스템 사이에 대화할 수 있는 상태를 만든다

세션 유지
통신 중간에 연결 상태를 관리한다.
1. 쿠키 발급 -> 사용자가 가지고 있기 때문에 보안에 취약
2. 세션 객체 -> 개인이 가지고 있는 것보다는 보안이 좀 나음 (서버에 부담이 간다.)
3. 토큰 발급 -> 암호화를 해서 발급

세션 종료
통신이 끝나면 세션을 정리한다.

모델링
- 테이블을 만들기 전에 요구사항을 잘 분석하고 무결성을 지키기 위한 계획

요구사항 분석
개념모델링 - 엔티티 구성, ERD 디자인
논리모델링 - 정규화, 속성 자료형, 제약조건 설정
물리모델링 - 실제로 테이블을 만드는 단계

정규화
- 이상현상을 제거하기 위해 테이블을 분리하는 것
ㄴ 삽입이상 : 데이터를 추가할때 필요없는 내용까지 추가되는 것
ㄴ 갱신이상 : 중복된 데이터가 있을때 일부분만 수정하는 것
ㄴ 삭제이상 : 데이터를 삭제할때 필요한 내용까지 삭제되는 것
1차
-모든 속성은 원자값이어야 한다.
2차
- 부분함수 종속을 해소
3차
- 이행함수 종속을 해소
BCNF
- 3차 정규화를 좀 더 엄격하게 관리(결정자는 반드시 후보키여야 한다.)
4차
- 관계 없는 속성은 분리한다.
5차
- 조인 종속을 제거한다.

SQL 함수
- 다양한 기능들을 제공하는 함수

문자열함수
숫자함수
날짜함수

- 단일행 함수 : 1개의 행에 대해서 함수를 적용하여 1개의 행을 반환
- 집계 함수 : 1개 이상의 행에 대해서 함수를 적용하여 1개의 값을 반환
COUNT,SUM,MAX,MIN,AVG

집계 함수(그룹 함수)
- 하나 이상의 행에 대한 값들에 대해 집계(개수,총합,최대,최소,평균값)하여 1개의 값으로 반환
- 일반적으로는 일반 속성과 집계함수를 같이 사용할 수는 없다.
- NULL값은 집계하지 않는다.

group by
- 같은 데이터를 묶어서 집계할 때 사용하는 문법
- 부서별, 상품별, 카테고리별 등...

select department_id, avg(salary)
from employees group by department_id

그룹을 지을 때 꼭 한가지 속성만 쓸 수 있는 것은 아님

관계형 데이터베이스 -> 테이블형태(행과 열로 이루어짐)

having
- group by로 만든 그룹을 조건으로 필터링을 할 때 사용하는 문법
- where은 -> 전체 행에 대해서 필터링
- having -> 그룹핑을 하고 난 다음 필터링

SELECT FROM WHERE GROUP BY HAVING

정렬(order by)
- 조회 결과를 원하는 순서로 정렬할 때 사용하는 문법
- 오름차순(ASC) : 작은거 -> 큰거
- 내림차순(DESC) : 큰거 -> 작은거
select 컬럼명 from 테이블명 order by 정렬기준컬럼 정렬방식;

순위를 정하는 함수 (윈도우 함수)
- ROW_NUMBER() : 무조건 1,2,3,4,처럼 번호를 붙인다.
- RANK() : 공동순위를 인정하고 다음 순위를 건너뛴다.
- DENSE_RANK() : 공동 순위를 인정하지만 다음 순위를 건너뛰지 않는다.
- NTILE(n) : 데이터를 n개의 그룹으로 나눈다.
순위함수() OVER(ORDER BY 정렬기준컬럼 정렬기준)

index
테이블에서 데이터를 더 빠르게 찾기 위해 만드는 검색용 목차
select * from student where name = '박민수';
인덱스가 없으면 MySQL은 데이터를 처음부터 하나씩 확인한다.
이런 방식을 Full Table Scan(전체 테이블 스캔)이라고 한다.

인덱스 생성 기본 문법
CREATE INDEX 인덱스명
ON 테이블명(컬럼명)

CREATE INDEX inx_student_name
ON student(name);

name값을 기준으로 정렬된 별도의 구조를 만든다.
[김철수] -> 데이터 위치
실제 테이블을 이름순으로 바꾸는 것이 아닌, 이름순으로 찾기 좋은 별도의 목차를 만든다.
쿼리를 실행하면 인덱스가 자동으로 사용됨

인덱스 확인법
SHOW INDEX FROM 테이블명;

인덱스 삭제
DROP INDEX 인덱스명 ON 테이블명;

테이블을 만들때 PK를 설정하면 MySQL은 자동으로 인덱스를 생성한다.

UNIQUE 제약조건도 자동으로 인덱스를 만든다.

인덱스의 장점
1. SELECT 속도가 향상된다
- 검색조건에 INDEX가 있으면 조회 속도가 빨라질 수 있다.
2. ORDER BY 성능 향상
- 정렬을 빠르게 할 수 있다.

인덱스의 단점
1. 저장공간이 추가로 필요하다.
- 인덱스는 별도의 자료구조이기 때문에 테이블 데이터를 저장하는 곳 외에 인덱스 공간이 추가로 필요하다.
2. INSERT가 느려질 수 있다.
- 데이터를 추가할 때 테이블에만 넣는 것이 아니라 인덱스도 같이 갱신해야 한다.
3. UPDATE가 느려질 수 있다.
- 인덱스가 걸린 컬럼을 수정하면 인덱스도 다시 정리해야 한다.
4. DELETE가 느려질 수 있다.
- 데이터를 삭제할 때도 인덱스에서 해당 값을 정리해야 한다.

인덱스를 걸면 좋은 컬럼
1. WHERE 조건에 자주 사용되는 컬럼
2. JOIN에 자주 사용되는 컬럼
3. ORDER BY에 자주 사용되는 컬럼
4. GROUP BY에 자주 사용되는 컬럼

인덱스를 걸면 애매한 컬럼
- 값의 종류가 너무 적은 컬럼
